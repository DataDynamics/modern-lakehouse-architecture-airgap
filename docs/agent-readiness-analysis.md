# Agent 대상 데이터 제공 요건 분석

고객이 제시한 목표를 현재 참조 아키텍처와 대조해, 부족한 부분과 구현 전에 결정해야 할
사항을 정리한 문서입니다.

> **고객 요구 원문**
>
> 데이터 수집/정제/가공, 벡터화, 지식화를 통해 Agent에게 리더블한 데이터를 제공하는 것이
> 목적입니다. 정형/비정형을 다루고, 정형은 새로 구축될 경영정보 마트 DB를 NL-to-SQL로
> 조회하고, 기타 문서나 매뉴얼 등은 시멘틱 레이어를 통한 RAG, KG로 제공하려고 합니다.

이 문서는 설계 확정본이 아니라 **검토 의견과 결정 대기 항목의 목록**입니다. 판단의 근거가
되는 현행 설계는 [architecture.md](architecture.md), 제품별 역할은
[solutions.md](solutions.md), 제품이 실제로 제공하는 기능은
[solution-features.md](solution-features.md)를 참고하십시오.

## 요구사항 해석

요구를 아키텍처 관점으로 옮기면 두 개의 독립 트랙과 하나의 공통 기반으로 나뉩니다.

| 트랙 | 대상 | 제공 방식 | 최종 소비자 |
|---|---|---|---|
| 정형 | 새로 구축될 경영정보 마트 DB | NL-to-SQL | Agent |
| 비정형 | 문서 · 매뉴얼 · 규정 | 시멘틱 레이어 기반 RAG, Knowledge Graph | Agent |
| 공통 기반 | 수집 · 정제 · 가공 · 벡터화 · 지식화 | 파이프라인 | 위 두 트랙 |

### 가장 중요한 변화 — 소비 주체가 사람에서 Agent로 바뀝니다

현행 아키텍처의 Layer 7은 사람을 전제로 설계되어 있습니다. Spotfire 대시보드, SQL
Client, Notebook은 모두 **사람이 스키마를 알고 있고, 결과가 이상하면 알아차린다**는
가정 위에 서 있습니다. Agent가 1급 소비자가 되면 이 가정이 전부 무너집니다.

| 항목 | 사람이 소비할 때 | Agent가 소비할 때 |
|---|---|---|
| 스키마 이해 | 담당자가 알거나 문서를 봄 | 기계가 읽을 수 있는 형태로 제공되어야 함 |
| 용어 해석 | 업무 지식으로 보완 | 명시적 매핑이 없으면 추론 실패 |
| 결과 검증 | 이상하면 알아차림 | 그럴듯한 오답을 그대로 반환 |
| 질의 패턴 | 소수의 정형화된 질의 | 예측 불가, 재시도 반복, 동시 다발 |
| 권한 | 로그인 사용자 = 조회 주체 | Agent 계정과 질문자가 분리됨 |
| 감사 | 사용자 질의 로그 | 질문 → 생성된 SQL → 결과의 3단 추적 필요 |

**"리더블한 데이터"의 실체는 데이터 자체가 아니라 데이터에 대한 메타데이터입니다.**
이 문서에서 지적하는 결손의 대부분이 여기서 나옵니다.

## 현행 아키텍처와의 차이

현재 설계에 이미 있는 것과 없는 것을 구분했습니다.

| 요구 구성요소 | 현행 상태 | 평가 |
|---|---|---|
| 수집 · 정제 · 가공 | CFM → Kafka → CDE Spark → Iceberg (medallion) | 갖춰짐. 그대로 활용 가능 |
| 문서 저장 존 | `s3a://lake/docs/` 를 raw · parsed · chunks · vectors 로 구분 | 경로 구조만 존재. 파이프라인 실체 없음 |
| 벡터 저장소 | Vector DB Support (Iceberg, PGVector, Elasticsearch) | 선택지만 나열. 선정·구성 미정 |
| NL-to-SQL | Starburst AI Features 에 한 줄 표기 | **뒷받침할 메타데이터 계층 전무** |
| RAG | Starburst AI Features 에 한 줄 표기 | 검색 파이프라인·권한 모델 미설계 |
| 경영정보 마트 DB | 없음 | **물리 구현체 미정. 최우선 결정 사항** |
| 시멘틱 레이어 | 없음 | 용어 정의부터 필요 |
| Knowledge Graph | 없음 | 저장소 · 온톨로지 · 추출 파이프라인 전부 없음 |
| 모델 서빙 | Cloudera AI 박스에 포함 | 폐쇄망 가용성 미검증. GPU 산정 없음 |
| Agent 런타임 | Cloudera AI Agent 한 줄 | 도구 정의 · 권한 · 세션 관리 미설계 |
| 품질 평가 체계 | 없음 | 운영 진입 조건인데 누락 |

정리하면 **데이터를 모으고 정제하는 부분은 준비되어 있고, 그것을 Agent가 이해할 수 있게
만드는 부분이 통째로 비어 있습니다.**

## 부족한 것 1 — 정형 트랙: NL-to-SQL을 지탱할 메타데이터

### NL-to-SQL의 정확도는 모델이 아니라 메타데이터가 결정합니다

이 점을 먼저 합의해야 합니다. 좋은 모델을 붙이면 해결되는 문제가 아닙니다. 특히 금융권
레거시 스키마는 NL-to-SQL에 가장 불리한 조건을 갖추고 있습니다.

- 컬럼명이 `CUST_NO`, `AMT_1`, `TRX_DT`, `YYYYMM` 형태의 축약형
- 한글 논리명이 별도 문서나 설계 도구에만 존재
- 코드성 컬럼이 지배적 (`STAT_CD = '01'` 이 무엇을 뜻하는지 데이터만 봐서는 알 수 없음)
- 동일 개념이 시스템마다 다른 컬럼명으로 존재

**질문 하나에 답하지 못하면 나머지는 무의미합니다.** "지난달 연체율 알려줘"라는 질문에
답하려면 Agent가 (1) 연체율의 정의, (2) 연체 상태를 나타내는 코드값, (3) 기준이 되는
날짜 컬럼, (4) 분모·분자에 해당하는 테이블과 조인 경로를 전부 알아야 합니다. 현재 이
정보는 어디에도 기계가 읽을 수 있는 형태로 존재하지 않습니다.

### 구축이 필요한 메타데이터

| 구성요소 | 내용 | 없을 때의 증상 |
|---|---|---|
| 비즈니스 용어집 | 업무 용어 ↔ 물리 테이블·컬럼 매핑 | 질문의 명사를 테이블로 연결하지 못함 |
| 지표 정의 | 계산식, 분모·분자, 예외 처리, 소관 부서 | 부서마다 다른 숫자가 나옴 |
| 코드값 사전 | 코드성 컬럼의 값과 의미 | `WHERE` 절을 생성하지 못함 |
| 조인 경로 정의 | 테이블 간 관계와 허용 조인 | 임의 조인으로 중복 집계 발생 |
| 기간·시점 규칙 | 기준일, 마감일, 영업일 정의 | "지난달"의 해석이 매번 달라짐 |
| 질의 예시 (few-shot) | 대표 질문–SQL 쌍 | 실무 표현을 이해하지 못함 |
| 접근 등급 | 테이블·컬럼별 민감도 | 조회하면 안 되는 것을 조회함 |

**지표 정의는 특히 조직적 합의가 필요한 항목입니다.** 기술 과제가 아니라 업무 과제이므로,
현업 부서와의 정의 확정 일정을 프로젝트 초기에 잡아야 합니다. 이 작업이 전체 일정의
임계 경로가 될 가능성이 높다고 봅니다.

### "시멘틱 레이어"라는 용어의 정리가 먼저 필요합니다

고객 요구에서 시멘틱 레이어는 비정형 쪽에 붙어 있습니다. 그런데 이 용어는 실무에서 두
가지 다른 뜻으로 쓰입니다.

| 구분 | 의미 | 대상 | 대표 구현 |
|---|---|---|---|
| 분석 의미 계층 | 지표·차원·조인 관계의 정의 | 정형 | dbt Semantic Layer, Cube, Starburst data products |
| 의미 검색 계층 | 임베딩 기반 유사도 검색 | 비정형 | 벡터 저장소 + 검색 API |

고객은 후자를 지칭한 것으로 읽히지만, **정작 시멘틱 레이어가 절실한 쪽은 정형 트랙**
입니다. 두 가지는 서로 다른 산출물이고 필요한 작업량도 다릅니다. 요건 협의 초기에 어느
쪽을 말하는지 확정하지 않으면, 산출물 인수 단계에서 인식 차이가 드러납니다.

의견을 드리면 **둘 다 필요하며, 별도의 구성요소로 명시해 설계에 반영해야 합니다.**

## 부족한 것 2 — 경영정보 마트 DB의 위치

고객은 "새로 구축될 경영정보 마트 db"라고 표현했습니다. 이 문장 하나가 아키텍처의 상당
부분을 좌우하는데, 현행 다이어그램에는 해당하는 상자가 없습니다.

### 두 가지 해석과 각각의 영향

| 해석 | 물리 구현 | 조회 경로 | 영향 |
|---|---|---|---|
| A. Gold 존이 마트 | Iceberg 테이블 (`s3a://lake/gold/`) | Trino Iceberg 커넥터 | 현행 설계 그대로. 추가 구성요소 없음 |
| B. 별도 RDBMS | Oracle, PostgreSQL 등 | Trino 페더레이션 커넥터 | **마트 적재 경로가 신설되어야 함** |

"db"라는 표현으로 보아 B일 가능성이 높다고 판단합니다. B라면 다음이 추가로 필요합니다.

- **CDE Spark → 마트 DB 적재 경로.** 현재 다이어그램의 Layer 5는 Layer 4와 왕복(4 ↔ 5)만
  있고, 외부 DB로 내보내는 경로가 없습니다
- 마트 DB의 이중화·백업 정책
- Iceberg Gold 와 마트 DB 사이의 **정합성 기준**. 두 곳에 같은 지표가 존재하게 되므로,
  어느 쪽이 정본인지 정해야 합니다
- 마트 DB에 대한 Trino 커넥터의 부하 통제 (리소스 그룹)

**이 결정이 나기 전에는 나머지 설계를 확정할 수 없습니다.** 가장 먼저 확인할 항목입니다.

## 부족한 것 3 — 비정형 트랙: 문서 파이프라인의 실체

현행 설계에 `docs/raw → parsed → chunks → vectors` 경로 구조는 정의되어 있고, 임베딩
모델 교체 시 `parsed/` 부터 재처리한다는 원칙도 서 있습니다. 이 부분은 방향이 맞습니다.
다만 각 단계를 무엇으로 수행할지가 비어 있습니다.

### 파싱 — 국내 금융권 특유의 난점

| 항목 | 검토 필요 사항 |
|---|---|
| HWP · HWPX | 국내 금융권 내부 문서의 상당수가 한글 문서. 폐쇄망에서 쓸 수 있는 파서 확보가 선결 과제 |
| 스캔 PDF | 약관·계약서 원본이 이미지인 경우 OCR 필요. 한국어 OCR 품질과 폐쇄망 반입 가능성 확인 |
| 표 구조 | 금리표·수수료표는 표 구조가 의미의 핵심. 단순 텍스트 추출 시 정보가 소실됨 |
| 문서 내 도표·이미지 | 텍스트만 추출할지, 멀티모달로 다룰지 결정 |

**표 추출 품질을 과소평가하지 않기를 권합니다.** 금융 문서에서 답변의 근거가 되는 숫자는
대부분 표 안에 있습니다.

### 청킹 — 문서 종류별로 전략이 달라야 합니다

| 문서 유형 | 권장 청킹 단위 | 이유 |
|---|---|---|
| 약관 · 규정 | 조 · 항 단위 | 인용 단위가 곧 조항이며, 근거 제시에 그대로 쓰임 |
| 업무 매뉴얼 | 절차 · 섹션 단위 | 절차 중간이 잘리면 실행 불가능한 답변이 생성됨 |
| 상품설명서 | 상품 단위 | 상품 간 정보가 섞이면 안 됨 |
| 회의록 · 보고서 | 의미 단락 단위 | 구조가 일정하지 않음 |

일괄 고정 길이 청킹으로 시작하면 재작업이 발생합니다.

### 문서 메타데이터 — RAG 품질을 좌우하는 실질 요소

벡터 유사도만으로는 다음을 구분할 수 없습니다. 청킹 단계에서 메타데이터로 부여하고,
검색 시 필터로 적용해야 합니다.

| 메타데이터 | 필요한 이유 |
|---|---|
| 시행일 · 폐지일 | **개정 전 약관이 검색되면 규정 위반 답변이 생성됩니다.** 유효 시점 필터가 필수 |
| 문서 버전 | 개정 이력 추적과 재처리 대상 판별 |
| 열람 권한 등급 | 권한 없는 사용자에게 내용이 노출되는 것을 차단 |
| 문서 종류 · 소관 부서 | 검색 범위 축소와 정확도 향상 |
| 원본 위치 · 페이지 | 근거 제시와 원문 확인 |

**시행일 관리가 특히 중요합니다.** 금융 약관은 개정 이력이 누적되고, "현재 유효한 내용"과
"과거 특정 시점에 유효했던 내용"이 모두 조회 대상이 됩니다. 벡터 검색에는 시점 개념이
없으므로 메타데이터 필터로만 해결됩니다.

### 저장소 선택

현행 문서에 Vector Store 선택 기준표가 이미 있어 판단 근거는 마련되어 있습니다. 다만
실제 선정은 문서 건수·갱신 빈도·권한 필터 요건이 확정된 뒤에 가능합니다. 한국어 문서
검색이 중심이라면 **BM25 키워드 검색과 벡터 검색을 결합한 하이브리드 구성**을 기본값으로
검토할 것을 권합니다. 금융 문서에는 상품명·조항 번호처럼 정확히 일치해야 하는 표현이
많아, 벡터 검색 단독으로는 놓치는 경우가 발생합니다.

## 부족한 것 4 — Knowledge Graph

현행 아키텍처에 KG는 어떤 형태로도 존재하지 않습니다. 저장소, 온톨로지, 추출
파이프라인, 조회 인터페이스가 전부 신규 설계 대상입니다.

### 결정이 필요한 항목

| 항목 | 선택지 | 고려 사항 |
|---|---|---|
| 그래프 저장소 | Neo4j, JanusGraph, PostgreSQL + Apache AGE, ArangoDB | 폐쇄망 반입·라이선스·운영 인력 |
| 온톨로지 범위 | 전사 vs 특정 도메인 | **범위를 좁혀 시작할 것을 강력히 권합니다** |
| 추출 방식 | 규칙 기반, LLM 기반, 혼합 | LLM 추출은 검증 절차가 반드시 동반되어야 함 |
| 활용 형태 | GraphRAG vs 독립 조회 도구 | Agent 도구 설계가 달라짐 |
| 갱신 주기 | 배치 재구축 vs 증분 갱신 | 문서 개정 시 그래프 정합성 유지 방식 |

### 저장 존 구조 보완

현행 `docs/` 존에는 KG 산출물을 둘 자리가 없습니다. 다음과 같은 확장을 제안합니다.

```
docs/raw/         원본 (현행)
docs/parsed/      텍스트 추출 결과 (현행)
docs/chunks/      청킹 결과 + 메타데이터 (현행)
docs/vectors/     임베딩 (현행)
docs/entities/    추출된 엔티티와 속성          ← 신설
docs/relations/   추출된 관계 (그래프 적재 원본)  ← 신설
```

엔티티·관계를 Iceberg 테이블로 남겨 두면 그래프 DB를 교체하거나 재구축할 때 추출
단계를 반복하지 않아도 됩니다. `parsed/` 부터 재처리한다는 현행 원칙과 같은 사고방식입니다.

### 온톨로지 설계에 대한 의견

전사 온톨로지를 먼저 설계하는 접근은 실패 확률이 높습니다. **답변해야 할 질문 목록에서
역산해 필요한 엔티티만 정의하는 방식**을 권합니다. 예를 들어 상품 문의 대응이 첫 목표라면
상품 · 약관 조항 · 수수료 · 대상 고객군 · 판매 채널 정도로 시작하고, 조직·규정·프로세스는
다음 단계로 미루는 방식입니다.

## 부족한 것 5 — 폐쇄망 모델 서빙 (선결 조건)

**이 항목은 다른 모든 설계의 전제이므로 가장 먼저 검증되어야 합니다.**

### 확인된 제약

[solution-features.md](solution-features.md) 작성 과정에서 확인한 바로, Starburst 문서가
명시하는 model provider 는 AWS Bedrock, OpenAI, Google Gemini, Azure OpenAI, Gemini API
로 **전부 외부 SaaS** 입니다. 폐쇄망에서는 어느 것도 호출할 수 없습니다.

따라서 다음 중 하나가 성립해야 합니다.

| 경우 | 결과 |
|---|---|
| Starburst 가 사내 호스팅 엔드포인트를 model provider 로 지원 | 현행 설계대로 Layer 6 에서 NL-to-SQL 수행 |
| 지원하지 않음 | **NL-to-SQL 을 Starburst 밖에서 구현해야 하며, 아키텍처가 바뀝니다** |

반입 예정 버전의 문서로 이 항목을 먼저 확인할 것을 권합니다.

### 필요한 모델과 자원 산정

현행 아키텍처에는 GPU 자원 산정이 전혀 없습니다. 최소 세 종류의 모델이 상시 서빙되어야
합니다.

| 모델 | 용도 | 고려 사항 |
|---|---|---|
| 임베딩 모델 | 문서 벡터화, 질의 벡터화 | **한국어 성능이 선정 기준**. 교체 시 전체 재색인 발생 |
| 생성 모델 (LLM) | NL-to-SQL, RAG 답변 생성 | 컨텍스트 길이, 한국어 품질, GPU 메모리 |
| 리랭커 | 검색 결과 재정렬 | 정확도 향상 대비 지연 증가 |

추가로 검토할 항목입니다.

- 초기 전량 색인에 필요한 처리량과 소요 시간 (문서 건수에 비례)
- 상시 질의 부하와 배치 색인 부하의 자원 분리
- 모델 파일의 폐쇄망 반입 절차와 갱신 주기
- 모델 교체 시 재색인 계획 (임베딩 모델 교체는 전체 재처리를 유발)

## 부족한 것 6 — Agent 런타임과 도구

현행 다이어그램에서 Agent 는 Cloudera AI 상자 안의 한 줄입니다. Agent 가 1급 소비자가
되는 구조에서는 별도 계층으로 다뤄야 합니다.

### 도구(tool) 정의

Agent 가 사용할 도구가 명확히 정의되어야 하며, 현재 세 번째 항목이 비어 있습니다.

| 도구 | 현행 상태 | 비고 |
|---|---|---|
| SQL 조회 | Starburst MCP Server 로 가능 | 읽기 전용 질의 도구 제공 |
| 문서 검색 | 미설계 | 벡터 + 키워드 하이브리드 검색 API 필요 |
| 그래프 질의 | **없음** | KG 조회용 도구·MCP 서버 신설 필요 |
| 지표 조회 | 미설계 | 의미 계층 기반의 정형 지표 조회 |

### 권한 모델 — 금융권에서 가장 중요한 설계 항목

Agent 가 자체 계정으로 데이터를 조회하면 **누가 무엇을 볼 수 있는지에 대한 통제가
무력화됩니다.** 권한 없는 사용자가 Agent 를 통해 우회 조회하는 경로가 생깁니다.

질문한 사용자의 권한으로 조회가 수행되어야 하며, 이는 다음 전 구간에 일관되게 적용되어야
합니다.

- Trino 질의 — user impersonation 으로 구현 가능
- 벡터 검색 — **검색 결과에 권한 필터가 적용되어야 함. RAG 구현에서 가장 어려운 부분**
- 그래프 질의 — 노드·엣지 단위 권한 모델 필요
- 문서 원본 접근 — MinIO IAM 정책과 연계

### 감사 추적

금융권에서는 "왜 이 답이 나왔는가"를 소명할 수 있어야 합니다. 다음이 함께 보존되어야
합니다.

```
질문(원문) → 검색된 근거(문서 조각 · 그래프 경로) → 생성된 SQL → 실행 결과 → 최종 답변
```

현행 설계에는 이 추적 체계가 없습니다. Starburst 의 query auditing 은 SQL 실행 시점만
남기므로, 그 앞단인 질문과 근거 선택 과정은 Agent 런타임에서 별도로 기록해야 합니다.

## 부족한 것 7 — 품질 평가 체계

**평가 체계 없이 운영에 들어가면 품질 저하를 인지할 방법이 없습니다.** 착수 시점에 함께
준비해야 하는 항목입니다.

| 대상 | 평가 방법 | 준비물 |
|---|---|---|
| NL-to-SQL | 골든 질의셋에 대한 SQL 정확도, 결과 일치율 | 대표 질문 100건 내외와 정답 SQL |
| 문서 검색 | 재현율, 정밀도, 상위 K 내 정답 포함률 | 질문–정답 문서 쌍 |
| 답변 품질 | 근거 인용률, 환각 발생률 | 평가 기준과 검토 절차 |
| 회귀 | 모델·데이터 변경 후 재측정 | 자동화된 평가 실행 환경 |

**환각 통제 방침도 함께 정해야 합니다.** 근거 문서를 찾지 못했을 때 답변을 생성하지 않고
"확인되지 않음"을 반환하도록 하는 것이 금융권에서는 대체로 안전한 기본값입니다.

## 부족한 것 8 — 새로 생기는 통제 우회 경로

현행 문서는 `4 → 7` S3 직접 접근 경로에 Starburst 마스킹이 적용되지 않는 문제를 이미
지적하고 있습니다. **벡터 저장소와 그래프 저장소는 같은 문제를 더 확대합니다.**

| 경로 | 통제 현황 | 위험 |
|---|---|---|
| Trino 경유 조회 | 행·열 수준 마스킹 적용 | 통제됨 |
| S3 직접 접근 | MinIO IAM 만 적용 | 기존 지적 사항 |
| **벡터 검색** | **통제 수단 미설계** | 문서 조각에 개인정보·내부정보가 포함된 채 검색됨 |
| **그래프 질의** | **통제 수단 미설계** | 관계 자체가 민감 정보일 수 있음 |

추가로 고려할 사항입니다.

- **임베딩도 보호 대상입니다.** 벡터에서 원문을 상당 부분 복원할 수 있다는 연구가 있으므로,
  개인정보가 포함된 문서의 임베딩은 원문과 동일한 수준으로 취급하는 것이 안전합니다
- 청킹 단계에서 비식별 처리를 선행할지, 검색 시점에 필터링할지 결정 필요
- 생성형 AI 활용에 관한 금융 감독 지침과 내부 규정의 적용 범위 확인

---

## 먼저 확정해야 할 결정 사항

의존 관계를 고려한 순서입니다. 위쪽 항목이 확정되지 않으면 아래 항목을 설계할 수 없습니다.

| 순위 | 결정 사항 | 확정되지 않으면 |
|---|---|---|
| 1 | 경영정보 마트의 물리 구현체 (Iceberg Gold vs 별도 RDBMS) | 적재 경로와 조회 경로 전체가 미정 |
| 2 | 폐쇄망 LLM·임베딩 서빙 가능 여부와 모델 선정 | 두 트랙 모두 착수 불가 |
| 3 | Starburst 의 사내 model provider 지원 여부 | NL-to-SQL 구현 위치가 바뀜 |
| 4 | 시멘틱 레이어의 정의 (분석 의미 계층 / 의미 검색 계층 / 둘 다) | 산출물 범위가 어긋남 |
| 5 | 대상 문서의 범위·형식·건수 | 파싱 도구와 자원 산정 불가 |
| 6 | KG 적용 범위와 온톨로지 경계 | 과대 설계 위험 |
| 7 | 권한 모델 (사용자 위임 방식) | 전 구간 재설계 위험 |
| 8 | 평가 기준과 골든 질의셋 소관 | 품질 판정 불가 |

## 아키텍처 다이어그램에 추가되어야 할 것

현행 7 Layer 구조에 다음 구성요소가 반영되어야 합니다.

| 구성요소 | 위치 | 성격 |
|---|---|---|
| 경영정보 마트 DB | Layer 4 인접 또는 신설 | 1번 결정에 따라 확정 |
| 의미 계층 (지표·용어·코드값) | Layer 6 인접 | 신설. NL-to-SQL 의 전제 |
| 벡터 저장소 | Layer 4 또는 Layer 6 | 현행은 선택지만 표기됨 |
| Knowledge Graph 저장소 | Layer 4 인접 | 신설 |
| 문서 처리 파이프라인 | Layer 5 내부 | 파싱 · OCR · 청킹 · 임베딩 단계 명시 |
| 모델 서빙 (Inference) | Layer 6 · 7 사이 | 현재 Cloudera AI 안에 묻혀 있음. 독립 표기 필요 |
| Agent 런타임과 도구 계층 | Layer 7 | 도구 목록과 권한 경로 명시 |

## 단계적 접근 제안

전체를 동시에 착수하는 것은 권하지 않습니다. 두 트랙의 난이도와 선행 조건이 다릅니다.

| 단계 | 범위 | 목적 |
|---|---|---|
| 1 | 폐쇄망 모델 서빙 검증, 마트 구현체 확정 | 선결 조건 해소 |
| 2 | 좁은 주제 하나로 문서 RAG 구축 (예: 특정 상품군 약관) | 파싱·청킹·검색 품질을 실제 문서로 확인 |
| 3 | 마트 일부 영역 NL-to-SQL (지표 10~20개) | 메타데이터 구축 공수의 실측 |
| 4 | 평가셋 기반 품질 측정과 개선 | 확대 여부 판단 근거 확보 |
| 5 | KG 도입 (2·3 단계에서 한계가 확인된 영역에 한정) | 필요성이 입증된 범위에만 적용 |

**2·3 단계를 먼저 수행해야 하는 이유**는 메타데이터 구축과 문서 파싱의 실제 공수가
프로젝트 규모를 좌우하는데, 이 값을 사전에 추정하기 어렵기 때문입니다. 좁은 범위에서
실측한 뒤 전체 계획을 세우는 편이 안전합니다.

KG 를 마지막에 둔 것은 우선순위가 낮아서가 아니라, **RAG 만으로 해결되지 않는 질문
유형이 무엇인지 확인된 뒤에 적용 범위를 정하는 것이 합리적**이기 때문입니다. 관계 추론이
필요한 질문의 비중을 모르는 상태에서 온톨로지를 먼저 설계하면 과대 설계가 되기 쉽습니다.

### 요구사항 관련

| 용어 | 설명 |
|---|---|
| Agent | 도구를 사용해 다단계 작업을 스스로 수행하는 AI 실행 단위. 이 문서에서는 데이터의 최종 소비자입니다 |
| 리더블한 데이터 | Agent 가 별도 설명 없이 해석할 수 있는 상태의 데이터. 실질적으로는 데이터에 부여된 메타데이터의 품질을 뜻합니다 |
| 정형 데이터 | 스키마가 정의된 테이블 형태의 데이터 |
| 비정형 데이터 | 문서·이미지 등 고정 스키마가 없는 데이터 |
| 벡터화 | 텍스트를 의미가 반영된 숫자 벡터로 변환하는 것 |
| 지식화 | 데이터에서 엔티티와 관계를 추출해 구조화된 지식으로 만드는 것 |
| 경영정보 마트 | 경영 의사결정용 지표를 집계해 담는 데이터 저장소 |

### 정형 트랙

| 용어 | 설명 |
|---|---|
| NL-to-SQL | 자연어 질문을 SQL 질의로 변환하는 기능 |
| 의미 계층 (Semantic Layer) | 지표·차원·조인 관계의 정의를 물리 스키마와 분리해 관리하는 계층 |
| 비즈니스 용어집 | 업무 용어와 물리 테이블·컬럼의 매핑 정의 |
| 지표 정의 | 지표의 계산식, 분모·분자, 예외 처리, 소관 부서를 명시한 정의 |
| 코드값 사전 | 코드성 컬럼의 값과 의미를 정리한 사전. `STAT_CD = '01'` 이 무엇인지에 해당합니다 |
| 조인 경로 정의 | 테이블 간 관계와 허용되는 조인 경로의 명시 |
| few-shot | 모델에 예시를 함께 제시해 원하는 형식의 출력을 유도하는 방식 |
| 골든 질의셋 | 정답이 확정된 평가용 질문 모음 |

### 비정형 트랙

| 용어 | 설명 |
|---|---|
| RAG | Retrieval-Augmented Generation. 관련 문서를 검색해 근거로 제공한 뒤 답변을 생성하는 방식 |
| KG (Knowledge Graph) | 엔티티와 그 관계를 그래프로 표현한 지식 구조 |
| GraphRAG | 그래프 탐색으로 근거를 수집해 RAG 에 활용하는 방식 |
| 온톨로지 | 대상 영역의 개념과 관계를 정의한 체계 |
| 엔티티 | 그래프의 노드가 되는 개체. 상품·고객·조항 등 |
| 관계 | 엔티티 사이의 연결. 그래프의 엣지에 해당합니다 |
| 청킹 | 긴 문서를 검색·임베딩에 적합한 크기로 나누는 작업 |
| 파싱 | PDF·HWP 등에서 텍스트를 추출하는 단계 |
| OCR | Optical Character Recognition. 이미지 속 문자를 텍스트로 인식하는 기술 |
| HWP · HWPX | 한글 워드프로세서의 문서 형식. 국내 금융권 내부 문서에 널리 쓰입니다 |
| 하이브리드 검색 | 키워드 검색(BM25)과 벡터 검색을 결합해 순위를 매기는 방식 |
| 리랭커 | 1차 검색 결과를 다시 정렬해 정확도를 높이는 모델 |
| 재현율 · 정밀도 | 각각 정답을 얼마나 빠뜨리지 않았는지, 결과 중 정답 비율이 얼마인지를 나타내는 지표 |
| 환각 | 모델이 근거 없는 내용을 사실처럼 생성하는 현상 |
| 재색인 | 임베딩 모델 교체 등으로 전체 문서를 다시 벡터화하는 작업 |

### 공통 기반

| 용어 | 설명 |
|---|---|
| 모델 서빙 | 학습된 모델을 호출 가능한 엔드포인트로 배포해 운영하는 것 |
| 추론 엔드포인트 | 모델에 입력을 보내 결과를 받는 API 접점 |
| model provider | AI 기능이 호출하는 추론 모델 공급자 |
| 임베딩 모델 | 텍스트를 벡터로 변환하는 모델. 한국어 성능이 선정 기준이 됩니다 |
| MCP | Model Context Protocol. Agent 가 외부 도구·데이터에 접근하기 위한 개방형 규약 |
| 도구 (tool) | Agent 가 호출할 수 있도록 정의된 기능 단위 |
| user impersonation | 질의를 요청한 사용자 자격으로 데이터에 접근하는 위임 방식 |
| 마스킹 | 민감 정보를 가리거나 대체해 조회 결과에 노출되지 않게 하는 기법 |
| 비식별 처리 | 개인을 특정할 수 없도록 데이터를 가공하는 것 |
| 감사 추적 | 질문부터 최종 답변까지의 과정을 소명 가능하도록 기록하는 것 |
| 임계 경로 | 전체 일정을 결정하는 작업 연쇄. 이 경로가 지연되면 프로젝트 전체가 지연됩니다 |
