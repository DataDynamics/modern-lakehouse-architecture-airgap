## 요구사항 해석

요구를 아키텍처 관점으로 옮기면 두 개의 트랙과 하나의 공통 기반으로 나뉩니다.

| 트랙 | 대상 | 제공 방식 | 최종 소비자 |
|---|---|---|---|
| 정형 | 새로 구축될 경영정보 마트 DB | NL-to-SQL | Agent |
| 비정형 | 문서 · 매뉴얼 · 규정 | 시멘틱 레이어 기반 RAG, Knowledge Graph | Agent |
| 공통 기반 | 수집 · 정제 · 가공 · 벡터화 · 지식화 | 파이프라인 | 위 두 트랙 |

### 소비 주체가 사람에서 Agent로 바뀝니다

현행 Layer 7은 사람을 전제로 설계되어 있습니다. Spotfire 대시보드, SQL Client, Notebook은
모두 **사람이 스키마를 알고 있고, 결과가 이상하면 알아차린다**는 가정 위에 서 있습니다.

| 항목 | 사람이 소비할 때 | Agent가 소비할 때 |
|---|---|---|
| 스키마 이해 | 담당자가 알거나 문서를 봄 | 기계가 읽을 수 있는 형태로 제공되어야 함 |
| 용어 해석 | 업무 지식으로 보완 | 명시적 정의가 없으면 추론 실패 |
| 결과 검증 | 이상하면 알아차림 | 그럴듯한 오답을 그대로 반환 |
| 질의 패턴 | 소수의 정형화된 질의 | 예측 불가, 재시도 반복 |
| 권한 | 로그인 사용자 = 조회 주체 | Agent 계정과 질문자가 분리될 수 있음 |
| 감사 | 사용자 질의 로그 | 질문 → 생성 SQL → 결과의 3단 추적 필요 |

**"리더블한 데이터"의 실체는 데이터 자체가 아니라 데이터에 대한 메타데이터입니다.**
이어지는 분석은 그 메타데이터를 어디서 얻고 무엇을 추가로 만들어야 하는지에 관한 것입니다.

## Starburst 중심 구성 — 문서 확인 결과

정형 트랙의 핵심은 Starburst가 Data Federation을 통해 원천의 메타데이터를 이미 알고
있다는 점입니다. 이 구성이 성립하는지 공식 문서로 확인한 결과를 정리합니다.

### Data Federation이 제공하는 메타데이터

Starburst는 커넥터를 통해 각 데이터 소스에 연결되는 순간 **기술 메타데이터를 자동으로
확보**합니다. 카탈로그 · 스키마 · 테이블 · 컬럼 · 데이터 타입이 여기 해당하며, 별도
수집 파이프라인을 만들 필요가 없습니다.

이 구조의 이점은 원천이 늘어나도 메타데이터 관리 지점이 하나로 유지된다는 것입니다.
경영정보 마트, Iceberg Gold, Kafka, 레거시 Oracle이 각각 어디에 있든 Agent 입장에서는
Starburst 하나만 바라보면 됩니다.

### MCP Server가 Agent에게 노출하는 도구

Starburst Enterprise는 MCP 서버를 내장하며, 인증된 stateless HTTP 엔드포인트로 다음
도구를 노출합니다.

| 도구 | 기능 |
|---|---|
| `queryReadOnly` | 읽기 전용 SQL 실행. 질의 ID, 컬럼 메타데이터(이름·타입), 행 데이터를 JSON으로 반환 |
| `searchDataProducts` | 데이터 상품의 이름 · 요약 · 설명과 포함된 뷰를 키워드로 검색 |
| `getDataProductDetails` | 특정 데이터 상품의 전체 메타데이터. 뷰·구체화 뷰의 컬럼, 타입, **설명**, 정의 포함 |
| `listParametrizedQueryTools` | 사전 정의된 파라미터화 질의 템플릿 목록 조회 |
| `parametrizedQuery` | 사전 승인된 SQL 템플릿을 파라미터 값만 받아 실행 |
| 데이터 상품 AI Agent | 데이터 상품 단위의 상태 유지 대화 세션을 MCP로 노출 |

주요 설정 속성입니다.

| 속성 | 기본값 | 비고 |
|---|---|---|
| `starburst.mcp.enabled` | — | MCP 서버 활성화 |
| `mcp.query.max-query-execution-time` | 5분 | 질의 실행 시간 상한 |
| `mcp.query.max-result-size` | 1MB | 범위 64KB ~ 8GB |
| `mcp.parametrized-tools.enabled` | — | 파라미터화 질의 도구 활성화 |
| `mcp.auth.scopes-supported` | — | OAuth 스코프 |

**금융권 관점에서 `parametrizedQuery`를 주목할 만합니다.** 자유 형식 NL-to-SQL을 전면
허용하는 대신, 승인된 SQL 템플릿에 파라미터만 채우게 하면 SQL 주입을 차단하고 조회 범위를
통제할 수 있습니다. 민감도가 높은 영역은 이 방식으로 시작하고, 낮은 영역만 자유 질의를
여는 단계적 개방이 현실적이라고 봅니다.

### NL-to-SQL

AI Data Assistant(AIDA)와 Starburst AI Agent가 담당합니다. 자연어 질문을 받아 스키마를
파악하는 탐색 질의를 먼저 수행한 뒤 최종 SQL을 생성·실행하고, 결과를 요약 · 관찰 ·
데이터 그리드 형태로 반환합니다. 후속 질문과 생성된 SQL에 대한 설명도 지원합니다.

| 속성 | 기본값 | 비고 |
|---|---|---|
| `starburst.agent.enabled` | `false` | AI Agent 활성화 |
| `ai.agent.allowed-models-regex` | 아래 참조 | 허용 모델 패턴 |
| `ai.agent.max-query-run-time` | — | 질의 시간 상한 |
| `ai.agent.data-profile.enabled` | `false` | 데이터 프로파일링 |
| `ai.agent.guardrails.enabled` | `true` | 가드레일 |
| `ai.agent.schema-link.max-request-concurrency` | 무제한 | 스키마 연결 시 동시 LLM 요청 수 |

`ai.agent.data-profile.enabled`는 **금융권에서 별도 검토가 필요한 항목**입니다.
프로파일링을 켜면 정확도가 올라가지만 데이터의 특성이 모델에 전달됩니다. 폐쇄망 내부
모델이라면 위험이 낮아지나, 어떤 정보가 모델로 넘어가는지는 확인하고 승인받는 편이
안전합니다.

### Model Provider — 폐쇄망에서 고객 보유 모델 사용

**문서로 확인된 결과, 폐쇄망에서 고객이 보유한 모델을 그대로 사용할 수 있습니다.**

Starburst 문서는 모델 통합 방식으로 Amazon Bedrock, **OpenAI & OpenAI API Compatible**,
Google Gemini Enterprise Agent Platform 세 가지를 제시하며, 다음과 같이 명시합니다.

> Starburst lets you integrate with compatible APIs from these supported providers,
> whether these external models are deployed **on-premises** or in the cloud.

자체 호스팅 모델을 쓰려면 제공자로 **OpenAI**를 선택하고 엔드포인트 URL에 사내 주소를
입력합니다. API 키는 해당 엔드포인트가 요구하지 않으면 생략할 수 있습니다.

이 아키텍처에서는 다음 연결이 성립합니다. Cloudera AI Inference Service가 OpenAI Python
SDK로 호출 가능한 OpenAI 호환 엔드포인트를 제공하므로, 외부 통신 없이 전 구간이 내부에서
닫힙니다.

```
Starburst AI (OpenAI 호환 제공자로 설정)
   → 사내 OpenAI 호환 엔드포인트 (Cloudera AI Inference Service 등)
      → 고객 보유 모델
```

다만 **모델 허용 목록은 확인이 필요합니다.** `ai.agent.allowed-models-regex`의 기본값은
검증된 모델군만 허용합니다.

```
(.*claude.*4.*)|(.*gpt-5.*)|(.*gemini-3.*)|(.*gemini-2.5.*)|(.*opus.*)|(.*qwen3.*)
```

고객이 보유한 모델(예: 한국어 특화 파인튜닝 모델)이 이 패턴에 걸리지 않으면 정규식을
직접 지정해 우회해야 하고, 이 경우 Starburst가 검증하지 않은 모델이 됩니다. **모델 연동
자체는 되지만 NL-to-SQL 품질은 모델에 따라 달라지므로, 고객 보유 모델로 실제 정확도를
측정하는 절차가 필요합니다.**

### AI Functions — 벡터화를 SQL로 수행

Starburst는 `starburst.ai` 스키마에 다음 함수를 제공합니다.

| 구분 | 함수 |
|---|---|
| 임베딩 | `generate_embedding()` |
| 프롬프트 | `prompt()` |
| 작업 | `analyze_sentiment()`, `classify()`, `fix_grammar()`, `mask()`, `translate()` |

`generate_embedding()`이 있으므로 **벡터화를 Spark 배치가 아니라 SQL로 수행하는 선택지가
생깁니다.** 문서 청크가 Iceberg 테이블에 있다면 SQL 한 문장으로 임베딩 컬럼을 채울 수
있습니다. 대량 초기 색인은 Spark가 유리하고, 증분 갱신은 SQL이 간편하므로 두 방식을 나눠
쓰는 구성을 검토할 만합니다.

## 이전 분석에서 정정한 사항

초판에서 사실과 다르게 판단한 부분입니다.

| 항목 | 초판의 서술 | 정정 |
|---|---|---|
| 폐쇄망 모델 서빙 | model provider가 전부 외부 SaaS이므로 폐쇄망에서 Starburst AI 사용 불가할 수 있음. 최우선 검증 대상 | **오류.** OpenAI 호환 엔드포인트를 지원하며 온프레미스 배포를 명시적으로 허용합니다. 선결 조건이 아닙니다 |
| NL-to-SQL 메타데이터 | 뒷받침할 메타데이터 계층이 전무함 | **과장.** 기술 메타데이터는 Federation으로 자동 확보됩니다. 추가로 필요한 것은 의미 메타데이터입니다 |
| 시멘틱 레이어 | 별도 구성요소로 신설 필요 | **부분 정정.** Starburst 데이터 상품의 설명 필드가 그 자리를 대신할 수 있습니다. 신설이 아니라 작성의 문제입니다 |

초판이 model provider 목록만 보고 폐쇄망 불가 가능성을 제기한 것이 원인이었습니다.
같은 문서의 "Compatible APIs" 항목을 확인하지 않은 판단 오류입니다.

## 남은 과제

Starburst가 상당 부분을 해결하지만, 다음은 여전히 별도 구축 대상입니다.

### 1. 의미 메타데이터 — 자동으로 얻어지지 않는 부분

Federation이 주는 것과 사람이 채워야 하는 것을 구분해야 합니다.

| 구분 | 내용 | 확보 방법 |
|---|---|---|
| 기술 메타데이터 | 카탈로그 · 스키마 · 테이블 · 컬럼 · 타입 | Federation으로 자동 |
| 의미 메타데이터 | 한글 논리명, 코드값 의미, 지표 정의, 조인 경로 | **작성 필요** |

금융권 레거시 스키마는 의미 메타데이터 없이는 NL-to-SQL이 성립하기 어렵습니다.

- 컬럼명이 `CUST_NO`, `AMT_1`, `TRX_DT` 형태의 축약형
- 한글 논리명이 설계 산출물에만 존재
- 코드성 컬럼이 지배적 (`STAT_CD = '01'`이 무엇인지 데이터만으로는 알 수 없음)

"지난달 연체율"에 답하려면 Agent가 연체율의 정의, 연체 상태 코드값, 기준 날짜 컬럼,
분모·분자의 테이블과 조인 경로를 알아야 합니다.

**작성 위치는 Starburst 데이터 상품의 설명 필드가 적절합니다.** `getDataProductDetails`가
컬럼 설명까지 반환하므로, 여기에 채워 넣으면 별도 저장소 없이 MCP를 통해 Agent에게
그대로 전달됩니다. Starburst의 AI agent 기반 데이터 상품 보강 기능으로 초안을 생성한 뒤
현업이 검수하는 방식이면 작성 부담을 줄일 수 있습니다.

| 항목 | 성격 | 비고 |
|---|---|---|
| 컬럼 한글 논리명 | 기존 산출물 활용 가능 | 설계서·표준 사전에서 이관 |
| 코드값 사전 | 기존 코드 마스터 활용 | 코드 테이블이 있으면 자동화 가능 |
| 지표 정의 | **현업 합의 필요** | 기술 과제가 아님 |
| 조인 경로 | 모델링 산출물 활용 | 허용 조인의 명시 |
| 질의 예시 | 신규 작성 | 대표 질문–SQL 쌍 |

**지표 정의가 임계 경로가 될 가능성이 높습니다.** 같은 지표를 부서마다 다르게 계산하는
경우가 흔하고, 이는 합의로만 해결됩니다. 프로젝트 초기에 일정을 확보해야 합니다.

### 2. 경영정보 마트의 물리 구현체

고객이 "새로 구축될 경영정보 마트 db"라고 표현한 대상이 현행 다이어그램에 없습니다.

| 해석 | 물리 구현 | 조회 경로 | 영향 |
|---|---|---|---|
| A. Gold 존이 마트 | Iceberg (`s3a://lake/gold/`) | Iceberg 커넥터 | 현행 설계 그대로 |
| B. 별도 RDBMS | Oracle, PostgreSQL 등 | 페더레이션 커넥터 | **적재 경로 신설 필요** |

"db"라는 표현으로 보아 B일 가능성이 높다고 봅니다. B라면 CDE Spark에서 마트 DB로 내보내는
경로가 필요한데, 현행 Layer 5는 Layer 4와의 왕복만 있고 외부 DB로 나가는 경로가 없습니다.
Iceberg Gold와 마트 DB에 같은 지표가 존재하게 되므로 어느 쪽이 정본인지도 정해야 합니다.

조회는 어느 쪽이든 Starburst 커넥터로 통일되므로, Agent 관점에서는 차이가 없습니다.

### 3. 비정형 트랙 — 문서 파이프라인

Starburst가 담당하지 않는 영역입니다. 현행 설계에 `docs/raw → parsed → chunks → vectors`
경로 구조와 재처리 원칙은 서 있으나, 각 단계의 구현이 비어 있습니다.

**파싱** — 국내 금융권 특유의 난점이 있습니다.

| 항목 | 검토 사항 |
|---|---|
| HWP · HWPX | 내부 문서 상당수가 한글 문서. 폐쇄망에서 쓸 파서 확보가 선결 |
| 스캔 PDF | 약관·계약서 원본이 이미지면 OCR 필요 |
| 표 구조 | 금리표·수수료표는 표 자체가 의미의 핵심. 텍스트만 뽑으면 소실됨 |

**답변 근거가 되는 숫자는 대부분 표 안에 있습니다.** 표 추출 품질을 과소평가하지 않기를
권합니다.

**청킹** — 문서 종류별로 전략이 달라야 합니다.

| 문서 유형 | 청킹 단위 | 이유 |
|---|---|---|
| 약관 · 규정 | 조 · 항 | 인용 단위가 곧 조항 |
| 업무 매뉴얼 | 절차 · 섹션 | 절차 중간이 잘리면 실행 불가능한 답변 생성 |
| 상품설명서 | 상품 | 상품 간 정보 혼입 방지 |

**문서 메타데이터** — 벡터 유사도만으로 구분되지 않는 것들입니다.

| 메타데이터 | 필요한 이유 |
|---|---|
| 시행일 · 폐지일 | **개정 전 약관이 검색되면 규정 위반 답변이 생성됩니다** |
| 문서 버전 | 개정 이력 추적, 재처리 대상 판별 |
| 열람 권한 등급 | 권한 없는 사용자에 대한 노출 차단 |
| 원본 위치 · 페이지 | 근거 제시와 원문 확인 |

한국어 문서 검색이 중심이라면 **BM25 키워드 검색과 벡터 검색을 결합한 하이브리드 구성**을
기본값으로 검토할 것을 권합니다. 상품명·조항 번호처럼 정확히 일치해야 하는 표현이 많아
벡터 검색 단독으로는 놓치는 경우가 생깁니다.

### 4. Knowledge Graph

현행 아키텍처에 KG는 존재하지 않으며, Starburst도 제공하지 않습니다. 저장소, 온톨로지,
추출 파이프라인, 조회 도구가 전부 신규 대상입니다.

| 항목 | 선택지 | 고려 사항 |
|---|---|---|
| 그래프 저장소 | Neo4j, JanusGraph, PostgreSQL + Apache AGE, ArangoDB | 폐쇄망 반입 · 라이선스 · 운영 인력 |
| 온톨로지 범위 | 전사 vs 특정 도메인 | **좁게 시작할 것을 권합니다** |
| 추출 방식 | 규칙 기반, LLM 기반, 혼합 | LLM 추출은 검증 절차 필수 |
| 활용 형태 | GraphRAG vs 독립 조회 도구 | Agent 도구 설계가 달라짐 |
| Agent 연동 | KG 조회용 MCP 서버 | **Starburst MCP가 대신하지 못하는 부분** |

저장 존도 보완이 필요합니다.

```
docs/entities/    추출된 엔티티와 속성          ← 신설
docs/relations/   추출된 관계 (그래프 적재 원본)  ← 신설
```

엔티티·관계를 Iceberg에 남겨 두면 그래프 DB를 교체하거나 재구축할 때 추출 단계를 반복하지
않아도 됩니다. `parsed/`부터 재처리한다는 현행 원칙과 같은 사고방식입니다.

전사 온톨로지를 먼저 설계하는 접근은 실패 확률이 높습니다. **답변해야 할 질문 목록에서
역산해 필요한 엔티티만 정의하는 방식**을 권합니다.

### 5. 권한과 감사

MCP 서버가 Starburst의 기존 인증 방식을 사용하므로 정형 트랙의 권한은 기존 체계로
연결됩니다. 다만 전 구간 일관성은 별도 설계가 필요합니다.

| 경로 | 통제 수단 | 상태 |
|---|---|---|
| Trino 질의 | Ranger 행·열 수준 통제, user impersonation | 기존 체계 활용 가능 |
| 벡터 검색 | **미설계** | 검색 결과에 권한 필터 필요 |
| 그래프 질의 | **미설계** | 노드·엣지 단위 권한 |
| S3 직접 접근 | MinIO IAM | 기존 지적 사항 |

**질문한 사용자의 권한으로 조회가 수행되어야 합니다.** Agent가 자체 계정으로 조회하면
권한 없는 사용자의 우회 조회 경로가 생깁니다.

감사 측면에서는 다음 전체가 보존되어야 합니다. Starburst의 query auditing은 SQL 실행
시점만 남기므로, 앞단은 Agent 런타임에서 별도로 기록해야 합니다.

```
질문(원문) → 검색된 근거(문서 조각 · 그래프 경로) → 생성된 SQL → 실행 결과 → 최종 답변
```

**임베딩도 보호 대상입니다.** 벡터에서 원문을 상당 부분 복원할 수 있으므로, 개인정보가
포함된 문서의 임베딩은 원문과 동일한 수준으로 취급하는 것이 안전합니다.

### 6. 품질 평가 체계

**평가 체계 없이 운영에 들어가면 품질 저하를 인지할 방법이 없습니다.** 고객 보유 모델을
사용하는 구성에서는 특히 그렇습니다. Starburst가 검증한 모델군 밖의 모델을 쓸 경우
정확도를 실측할 수단이 반드시 있어야 합니다.

| 대상 | 평가 방법 | 준비물 |
|---|---|---|
| NL-to-SQL | 골든 질의셋의 SQL 정확도, 결과 일치율 | 대표 질문 100건 내외와 정답 SQL |
| 문서 검색 | 재현율, 정밀도, 상위 K 내 정답 포함률 | 질문–정답 문서 쌍 |
| 답변 품질 | 근거 인용률, 환각 발생률 | 평가 기준과 검토 절차 |
| 회귀 | 모델·데이터 변경 후 재측정 | 자동화된 평가 실행 환경 |

근거를 찾지 못했을 때 답변을 생성하지 않고 "확인되지 않음"을 반환하도록 하는 것이
금융권에서는 안전한 기본값입니다.

### 7. 자원 산정

폐쇄망 모델 서빙이 가능하다는 것과 자원이 준비되었다는 것은 다른 문제입니다. 현행
아키텍처에 GPU 산정이 없습니다.

| 모델 | 용도 | 고려 사항 |
|---|---|---|
| 임베딩 모델 | 문서·질의 벡터화 | 한국어 성능이 선정 기준. 교체 시 전체 재색인 |
| 생성 모델 | NL-to-SQL, RAG 답변 생성 | 컨텍스트 길이, 한국어 품질, GPU 메모리 |
| 리랭커 | 검색 결과 재정렬 | 정확도 향상 대비 지연 증가 |

- 초기 전량 색인의 처리량과 소요 시간
- 상시 질의 부하와 배치 색인 부하의 자원 분리
- `ai.agent.schema-link.max-request-concurrency`가 기본 무제한이므로, 스키마 연결 단계의
  동시 LLM 요청이 서빙 자원을 점유할 수 있습니다. 상한 설정 검토 필요
- `mcp.query.max-result-size` 기본 1MB. Agent가 받는 결과가 잘릴 수 있으므로 용도에 맞춰
  조정 필요

## 결정이 필요한 사항

문서 확인으로 해소된 항목을 제외하고 갱신한 목록입니다.

| 순위 | 결정 사항 | 확정되지 않으면 |
|---|---|---|
| 1 | 경영정보 마트의 물리 구현체 (Iceberg Gold vs 별도 RDBMS) | 적재 경로가 미정 |
| 2 | 고객 보유 모델의 선정과 `ai.agent.allowed-models-regex` 적용 | NL-to-SQL 품질을 예측할 수 없음 |
| 3 | 의미 메타데이터 작성 범위와 소관 (특히 지표 정의) | 정형 트랙 착수 불가 |
| 4 | 자유 NL-to-SQL vs 파라미터화 질의의 적용 경계 | 보안 검토 통과 여부 불확실 |
| 5 | 대상 문서의 범위 · 형식 · 건수 | 파싱 도구와 자원 산정 불가 |
| 6 | KG 적용 범위와 온톨로지 경계 | 과대 설계 위험 |
| 7 | 벡터 · 그래프 경로의 권한 모델 | 통제 우회 경로 잔존 |
| 8 | 평가 기준과 골든 질의셋 소관 | 품질 판정 불가 |
| 9 | `ai.agent.data-profile.enabled` 활성화 여부 | 정확도와 데이터 노출의 절충 미결 |

## 다이어그램에 반영할 구성요소

| 구성요소 | 위치 | 성격 |
|---|---|---|
| 경영정보 마트 DB | Layer 4 인접 또는 신설 | 1번 결정에 따라 확정 |
| Starburst MCP Server | Layer 6 | 기존 AI Features 안에 있으나 Agent 접점이므로 독립 표기 |
| 모델 서빙 (OpenAI 호환 엔드포인트) | Layer 6 · 7 사이 | Starburst와 Agent가 공유하는 공급자 |
| 벡터 저장소 | Layer 4 또는 6 | 현행은 선택지만 표기 |
| Knowledge Graph 저장소 | Layer 4 인접 | 신설 |
| 문서 처리 파이프라인 | Layer 5 내부 | 파싱 · OCR · 청킹 · 임베딩 명시 |
| Agent 런타임과 도구 계층 | Layer 7 | 도구 목록과 권한 경로 명시 |

## 단계적 접근

| 단계 | 범위 | 목적 |
|---|---|---|
| 1 | 사내 OpenAI 호환 엔드포인트 구성, Starburst AI 연동, 모델 허용 규칙 확정 | 연결 검증 |
| 2 | 마트 일부 영역의 데이터 상품 정의와 설명 작성 → NL-to-SQL 시험 (지표 10~20개) | 의미 메타데이터 작성 공수 실측 |
| 3 | 좁은 주제의 문서 RAG 구축 (예: 특정 상품군 약관) | 파싱 · 청킹 · 검색 품질 확인 |
| 4 | 골든 질의셋 기반 품질 측정 | 고객 보유 모델의 실제 정확도 확보 |
| 5 | KG 도입 (2 · 3단계에서 한계가 확인된 영역에 한정) | 필요성이 입증된 범위에만 적용 |

2단계를 우선하는 이유는 **의미 메타데이터 작성 공수가 프로젝트 규모를 좌우하는데 사전
추정이 어렵기 때문**입니다. 지표 10~20개로 실측한 뒤 전체 계획을 세우는 편이 안전합니다.

KG를 마지막에 둔 것은 우선순위가 낮아서가 아니라, RAG만으로 해결되지 않는 질문 유형이
확인된 뒤에 적용 범위를 정하는 것이 합리적이기 때문입니다.

### 요구사항

| 용어 | 설명 |
|---|---|
| Agent | 도구를 사용해 다단계 작업을 스스로 수행하는 AI 실행 단위. 이 문서에서는 데이터의 최종 소비자입니다 |
| 리더블한 데이터 | Agent가 별도 설명 없이 해석할 수 있는 상태의 데이터. 실질적으로는 메타데이터의 품질을 뜻합니다 |
| 정형 · 비정형 데이터 | 스키마가 정의된 테이블 형태의 데이터와, 고정 스키마가 없는 문서·이미지 |
| 벡터화 | 텍스트를 의미가 반영된 숫자 벡터로 변환하는 것 |
| 지식화 | 데이터에서 엔티티와 관계를 추출해 구조화된 지식으로 만드는 것 |
| 경영정보 마트 | 경영 의사결정용 지표를 집계해 담는 데이터 저장소 |

### Starburst 관련

| 용어 | 설명 |
|---|---|
| Data Federation | 데이터를 모으지 않고 여러 원천을 질의 시점에 통합 조회하는 방식 |
| 기술 메타데이터 | 카탈로그 · 스키마 · 테이블 · 컬럼 · 타입. Federation으로 자동 확보됩니다 |
| 의미 메타데이터 | 한글 논리명, 코드값 의미, 지표 정의, 조인 경로. 사람이 작성해야 합니다 |
| 데이터 상품 (Data Product) | 목적별로 정의·게시해 재사용하는 데이터 묶음. 설명 필드가 의미 메타데이터의 보관 위치가 됩니다 |
| MCP | Model Context Protocol. Agent가 외부 도구·데이터에 접근하기 위한 개방형 규약 |
| `queryReadOnly` | 읽기 전용 SQL을 실행하는 MCP 도구 |
| `parametrizedQuery` | 사전 승인된 SQL 템플릿에 파라미터만 받아 실행하는 MCP 도구 |
| 스키마 연결 (schema linking) | 질문에 관련된 스키마 요소를 찾아 연결하는 NL-to-SQL 내부 단계 |
| 데이터 프로파일링 | 데이터의 분포·특성을 파악해 SQL 생성 정확도를 높이는 기능 |
| 가드레일 (guardrails) | AI 기능의 오·남용을 막는 안전장치 |
| AIDA | AI Data Assistant. 자연어 질의를 SQL로 변환·실행하는 대화형 어시스턴트 |
| AI Functions | SQL에서 호출하는 임베딩 · 프롬프트 · 분류 등의 함수 |
